### 1.2 Die vier Optionen

**(a) C++-Kern als Qt-freie Bibliothek herauslösen, C-ABI, Rust-Crate `dab-core` wrappt in-process**

- Vorgehen: `libdabcore` ohne Qt; ~35 C-Funktionen (`dab_open`, `dab_set_channel`,
  `dab_select_service`, `dab_set_callback`, `dab_read_audio`, ...); Ereignisse als
  serialisierte Bytes (postcard/CBOR) über einen Callback; Rust: handgeschriebene
  `extern "C"`-Deklarationen (bindgen lohnt bei ~35 Funktionen nicht), darüber crossbeam.
- Vorteile: ein Prozess, minimale Latenz, große Puffer (Spektrum, Audio) ohne Pipe-Kopie;
  DSP-Qualität bleibt 1:1.
- Nachteile: Toolchain-Mix MinGW-DLL in MSVC-Rust-Prozess (Abschnitt 3): funktioniert, aber
  jede Grenzverletzung (C++-Exception, STL-Typ, `free` auf der falschen Seite) ist ein
  Absturz ohne Diagnose. `cxx` ist damit nicht nutzbar (cxx kompiliert die Brücke mit dem
  Rust-Host-Compiler cl.exe). USB-Abriss/libhackrf-Absturz reißt die GUI mit. Zwei
  Debugger-Welten (gdb vs. WinDbg) im selben Prozess.

**(b) Kompletter Rust-Rewrite des DSP**

- Rust-Ökosystem (Web-Recherche 2026-09-11; Unsicherheiten markiert):
  - `williamyang98/dab-ofdm-rust`: Port nur des OFDM-Demodulators aus williamyang98/DAB-Radio
    (C++); laut Autor "slower than the C++ version due to the lack of SIMD acceleration",
    deklariert als Sprach-Testprojekt. Kein FIC/MSC/Viterbi/AAC.
  - Ein reifes, gepflegtes Voll-Rust-DAB-Crate (OFDM + Viterbi + RS + FIC + MSC + PAD + MOT)
    konnte ich **nicht** finden; der Crate-Name `dab` ist belegt, aber nicht als
    vollständiger Decoder erkennbar (unsicher, nicht im Detail geprüft). `F4JTV/dab_decoder`
    ist ein SDR++-Modul, das den welle.io-C++-Backend wrappt, also derselbe Ansatz wie (a).
  - Bausteine: `rustfft` (AVX, sehr schnell), `hackrfone`/`seify` (HackRF), `cpal` (Audio),
    `fdk-aac`/`fdk-aac-sys` (Bindings, gleiche Lizenzlage wie heute), `symphonia` (AAC-LC
    in Rust, **ohne SBR/PS**, für DAB+ praktisch unbrauchbar, da fast alle Dienste HE-AAC
    v1/v2 senden), `mp3lame-encoder`, `id3`, `mp4`.
  - Viterbi in Rust mit `std::arch` AVX2 ist machbar, aber exakt die Stelle, die im Fork
    jetzt gemessen optimal ist.
- Aufwand realistisch: 8-12 k Zeilen Rust; darunter die bereits einmal gescheiterten
  Stellen (DQPSK-Demapping mit Soft-Bits, EEP/UEP-Depuncturing-Tabellen,
  Zeit-Deinterleaver 16 Frames, Superframe-Sync mit Firecode + RS(120,110)). Bei Vollzeit
  Monate; nebenher deutlich länger. Ergebnis wäre anfangs schlechter als der bestehende Kern
  (Sync-Robustheit, Empfindlichkeit aus dem QA-Report).
- Risiko: hoch. Memory: "kein Rewrite in Rust". Einziger echter Gewinn: eine Toolchain und
  `cargo build` ohne CMake.
- Fazit: nicht jetzt. Architektur aber so bauen, dass ein späterer Rust-Kern hinter
  derselben Command/Event-API austauschbar ist.

**(c) C++-Kern behalten, Kommandos/Events als C++-Threads + Queues, Rust nur dünne FFI**

- Im Grunde (a) mit der Queue auf der C++-Seite (eigene SPSC-Queues oder
  `moodycamel::ConcurrentQueue`). Empfehlung: Queues immer auf der Rust-Seite (crossbeam);
  C++ liefert nur einen synchronen Callback `on_event(const uint8_t*, size_t)` aus dem
  jeweiligen Kernthread. Für Kommandos genügt eine `std::mutex`-Queue, die der OFDM-Thread
  zwischen zwei Frames leert. (Heute ruft `RadioInterface` Methoden auf `ofdmHandler`
  direkt aus dem GUI-Thread auf, teils thread-unsicher, "funktioniert".)

**(d) dab-core als separater Prozess (IPC über stdin/stdout, Named Pipe oder WebSocket)**

- Vorgehen: `dabcored.exe` (MinGW-gebaut, MSYS2-DLLs daneben) spricht ein
  längenpräfixiertes Binärprotokoll (oder JSON-Lines für Steuerung + Binärframes für
  Audio/Spektrum) über stdin/stdout. Die Tauri-App startet ihn als Kindprozess
  (`CREATE_NO_WINDOW`); die Rust-Crate `dab-core` liefert `Sender<Command>` /
  `Receiver<Event>`. Audio bleibt **im Kernprozess** (PortAudio, wie heute) - die GUI
  schickt nur `SetVolume`. Alternativ streamt der Kern PCM (48 kHz stereo float = 384 kB/s,
  trivial für eine Pipe) und Rust spielt per `cpal`.
- Vorteile:
  - Toolchain-Konflikt verschwindet vollständig: Kern = MinGW/CMake wie heute, Rust = MSVC
    wie Tauri verlangt. Keine ABI-Grenze in-process.
  - Crash-Isolation: reißt libhackrf/USB den Kern, startet die GUI ihn neu (Presets, Timer,
    Timeshift-Zustand der GUI-Schicht bleiben).
  - **Der Kernprozess ist zugleich das Headless-CLI**: `dabcored --file Warntag.uff
    --service 0xD220 --wav out.wav --events events.jsonl` = automatisierte Regressionstests
    am Warntag-Mitschnitt ohne GUI. Meilenstein M0 wird damit Produkt-Artefakt, nicht
    Wegwerf-Tool. (Heute ist Warntag-Replay nur per GUI + Screenshot prüfbar, siehe
    `Warntag-2026\ANLEITUNG-Warntag.txt`.)
  - "GUI-Technik bleibt austauschbar" ist maximal erfüllt: alles, was einen Kindprozess
    starten kann (Python, Rust-TUI, Web-Remote), fährt den Kern.
  - Lizenz: GPLv3-Kern + GPLv3-GUI, unproblematisch. (FDK-AAC: siehe 5.3; die Prozessgrenze
    ändert daran nichts, weil der Kern selbst FDK linkt.)
- Nachteile:
  - Zwei Prozesse verwalten (Start, Beenden bei GUI-Absturz: Kern beendet sich bei EOF an
    stdin; einfach).
  - Spektrum (2048 float @ 10 Hz = 80 kB/s) und PCM (384 kB/s) laufen über die Pipe;
    für Windows-Pipes vernachlässigbar (zig MB/s), aber nicht zero-copy. Roh-IQ (4 MB/s)
    darf nie über die Pipe, muss es auch nicht.
  - Latenz Kommando -> Reaktion: < 1 ms zusätzlich; irrelevant.
  - Rust deserialisiert Ereignisse (serde + `postcard`/`rmp-serde` oder JSON-Lines).

### 1.3 Empfehlung

**Option (d) als Zielarchitektur, innen nach (a)/(c) strukturiert:**

1. Der C++-Kern wird zu einer **Qt-freien statischen Bibliothek `libdabcore`** mit einer
   Klasse `DabCore` (Kommandos als Methoden, Ereignisse über
   `std::function<void(const Event&)>` aus dem jeweiligen Kernthread). Kein Qt, keine
   QSettings. Das ist die eigentliche Arbeit (Abschnitt 2).
2. Darüber ein dünnes `dabcored.exe` (300-500 Zeilen): Ereignisse -> stdout, Kommandos <-
   stdin, Kommandozeilenoptionen für Headless-Betrieb.
3. Rust-Workspace: `dab-api` (Command/Event-Enums, serde), `dab-core` (spawnt Prozess,
   liefert crossbeam-Kanäle, `trait CoreBackend`), `dab-cli` (Testtreiber), Tauri-App.
4. Weil `libdabcore` eine saubere C++-API hat, ist später **ohne Änderung der Rust-API**
   eine In-Process-Variante (Option a, C-ABI-DLL + `libloading`) oder ein Rust-Kern
   (Option b) als weiteres `CoreBackend` einsetzbar.

Warum nicht sofort (a): Der Toolchain-Mix ist beherrschbar, kostet aber bei jedem Problem
Zeit, und der Gewinn (kein Kindprozess) ist bei Audio im Kern praktisch null. Der
Headless-Prozess ist zugleich das Testwerkzeug, das dem Projekt fehlt.

Warum nicht (b): siehe oben; das Memory ist eindeutig und die Recherche zeigt kein
Rust-Fundament, das die Lücke schließt.

Vom User-Wunsch "cargo workspace, crossbeam/tokio mpsc" bleibt alles auf der Rust-Seite
erhalten. Nuance: `dab-core` ist ein Rust-Crate, das den Kern **besitzt und kapselt**,
nicht eines, das ihn **implementiert**. Das muss der User bestätigen (Frage 1).

## 3. Toolchain-Konflikt Windows (MinGW-C++ vs. MSVC-Rust)

### 3.1 Fakten

- Tauri 2 unterstützt das GNU-Target auf Windows offiziell **nicht** ("Tauri does not
  officially support the gnu toolchain on Windows", Prerequisites-Doku); bekannte Fehler wie
  "export ordinal too large" beim Linken mit `x86_64-w64-mingw32-gcc` (tauri-apps/tauri
  #10843). wry/`webview2-com` sind auf MSVC ausgelegt, der Bundler (NSIS/MSI) ebenfalls.
- Lokal ist nur MSVC-Rust installiert; passt.
- Der C++-Kern hängt an MSYS2-Paketen: FFTW, FDK-AAC, faad2, libhackrf+libusb, PortAudio,
  LAME. Alle gibt es auch für MSVC (vcpkg: fftw3, fdk-aac, libusb, portaudio, mp3lame;
  libhackrf per CMake). Die Quellen enthalten aber GCC-Spezifisches: `ringbuffer.h`
  (`asm volatile("mfence")`, `__sync_synchronize`), `viterbi.cpp` mit `-mavx2 -msse4.1`
  (MSVC: `/arch:AVX2` + `__cpuid`-Dispatch prüfen), `mm_malloc.h`, `-municode`,
  `usleep()`. Ein MSVC-Port des Kerns ist möglich (1-2 Tage Build + Performance-Nacharbeit),
  bringt außer "eine Toolchain" nichts; der DSP wurde mit GCC gemessen.

### 3.2 Bewertung

| Variante | Machbarkeit | Bewertung |
|---|---|---|
| Rust auf `x86_64-pc-windows-gnu`, alles MinGW | Kern trivial, Tauri nicht unterstützt, Bundler/WebView2 fraglich | **Nein** |
| Kern als **DLL mit reiner C-ABI** (MinGW), Rust-MSVC lädt per `libloading` | Funktioniert. Regeln: nur C-Typen/POD, keine Exceptions über die Grenze (jeder Export in `try/catch(...)`), Speicher nur auf der allokierenden Seite freigeben, Callbacks `extern "C"`; `libstdc++-6.dll`, `libgcc_s_seh-1.dll`, `libwinpthread-1.dll` mitliefern oder `-static-libstdc++ -static-libgcc`; keine Import-Lib nötig bei `libloading` | **Ja, als spätere Option (a)** |
| Kern als **eigener Prozess** (MinGW), IPC | Kein Grenzproblem; Toolchains getrennt | **Empfohlen** |
| Kern nach MSVC portieren, `cxx`-Crate | 1-2 Tage Build-Port + unbekannte Performance-Nacharbeit; ermöglicht `cxx` und ein Debugger | Nur wenn (d)/(a) unhandlich werden |

`bindgen` bräuchte libclang (MSYS2 clang 20 vorhanden), lohnt bei ~35 Funktionen nicht;
`cbindgen` ist die Gegenrichtung (Rust -> C-Header), nicht benötigt.

### 3.3 Empfehlung

MSVC-Rust für Workspace + Tauri; MinGW/CMake/Ninja für `libdabcore` + `dabcored.exe`;
Kopplung per Kindprozess. Cargo ruft CMake **nicht** automatisch (kein `build.rs` über zwei
Toolchains): `tools/build-core.ps1` baut den Kern und legt `dabcored.exe` + DLLs nach
`apps/desktop/src-tauri/resources/core/`; Tauri bündelt sie als `resources`. Für den
Portable-Zip kopiert `tools/deploy-portable.ps1` alles in einen Ordner (4.5).

    EPG, EWS: einzeln, sofort.

- Zustand: Rust-Seite hält den "Truth-State" (Ensemble-Liste, Service, Timeshift-Position,

## 5. Neue Funktionen im Detail

### 5.1 Zehn Stationsspeicher

**Ist-Zustand:** Qt-DAB hat "Favoriten" (`main/ensemble-handler.cpp` Z. 60-420,
`~/.qt-dab-presets.xml`, Elemente `<preset SERVICE_NAME="..." CHANNEL="..."/>`, beliebig
viele, per Rechtsklick) und "letzter Dienst je Kanal" (INI `channelPresets`, radio.cpp
Z. 2292). Kein Zehnfach-Speicher, keine Zifferntasten.

**Datenmodell (Rust, `presets.json`):**
```rust
struct Preset { slot: u8 /*0..9*/, channel: String /*"5C"*/, eid: u16, sid: u32,
                scids: u8, name: String, logo_path: Option<PathBuf>, stored_at: DateTime }
```
Schlüssel ist `(channel, sid)`; Name/Logo sind Anzeige-Cache (der Sendername kommt beim
Empfang ohnehin aus FIG 1/1). Leerer Slot = `None`.

**Verhalten:**
- Aufruf: Klick auf Slot-Button, Tasten `1`-`9`, `0` (Slot 10). Gleicher Kanal ->
  `SelectService` (~0,3-1 s bis Audio, Backend-Neustart + AAC-Sync). Anderer Kanal ->
  `SetChannel` + warten auf `EnsembleFound`/`ServiceAdded(sid)` -> `SelectService`;
  Umschaltzeit 1,5-3 s (Retune ~100 ms, Sync ~0,5-1 s, FIC-Vollständigkeit bis ~1 s).
  Zwischenzustand in der UI anzeigen ("suche 5C ...").
- Belegen: Rechtsklick auf Slot -> "Mit aktuellem Sender belegen"; Langdruck (500 ms)
  wie im Autoradio; Drag aus der Senderliste auf den Slot; Tastatur `Strg+Ziffer`.
  Überschreiben mit Bestätigung (Frage 4).
- Rand: Dienst nach Retune nicht gefunden (Ensemble umkonfiguriert, Empfang weg) ->
  Meldung, Preset behalten. Sub-Service (SCIdS != 0) unterstützen (Qt-DAB kann Secondary
  Services). Presets während Aufnahme: Umschaltsperre greift (wie heute).
- Ort: vollständig **GUI/App-Schicht** (Rust-State + Svelte); der Kern kennt keine Presets.
  Timer könnten künftig auf Presets zeigen.

### 5.2 Timeshift, Länge frei definierbar

**Was puffern? (Zahlen für 5C-Bundesmux, DAB+):**

| Ebene | Datenrate | 1 h | Umschalten in der Vergangenheit? | Anzapfpunkt im Code |
|---|---|---|---|---|
| Roh-IQ int8 2,048 MS/s | 4,1 MB/s = 245 MB/min | 14,7 GB | ja, sogar Kanal-fremd nein | Device-Ring (`_I_Buffer`); Warntag-Datei: 13,8 GB / 56 min |
| CIF Soft-Bits (int8) alle Dienste | 55 296 B / 24 ms = 2,3 MB/s = 138 MB/min | 8,3 GB | ja, innerhalb des Ensembles (Backend läuft nach) | `mscHandler::processMsc` (cifVector) |
| Subchannel-Hardbits **eines** Dienstes nach Viterbi (= DAB+-Superframes) | Bitrate, z. B. 72-96 kbit/s = 0,55-0,72 MB/min | 33-43 MB | nein (nur der gepufferte Dienst) | `Backend::processSegment` -> `backendDriver::addtoFrame` (outData je 24 ms) |
| AAC-AUs nach RS/Firecode (LATM) | ~gleich | ~40 MB | nein | `mp4Processor::processSuperframe`, `au_start[]` (Z. 200-290), heute Frame-Dump `.aac` |
| PCM 48 kHz stereo int16 | 192 kB/s = 11,5 MB/min | 690 MB | nein | `converter_48000` Ausgang |

**Empfehlung:** Puffern auf Ebene **Subchannel-Hardbits des gewählten Dienstes** (24-ms-
Blöcke inkl. der darin liegenden PAD-Daten, also DLS/DL+/MOT-Slides bleiben zeitrichtig
erhalten). Vorteile: kleinste Datenmenge (1 h = ~40 MB RAM, 8 h = 320 MB, "frei
definierbar" ist damit RAM-Frage; Disk-Ring optional), verlustfrei, die Wiedergabe läuft
durch exakt denselben `mp4Processor`/FDK-Pfad, und derselbe Puffer liefert **rückwirkende
Aufnahme** ("die letzten 20 Minuten als Datei speichern") und den Vorlauf für die
Musik-Trennung (5.3). Nachteil: Beim Dienstwechsel beginnt der Puffer neu (wie bei
Hardware-Radios mit Timeshift). Ensemble-weites Timeshift (CIF-Ebene, 8 GB/h auf Disk)
wäre technisch möglich (Backend beim Rückspulen über den CIF-Ring neu füttern), ist aber
für den Alltag unverhältnismäßig (Frage 2).

**Kernseitig (C++):** Klasse `TimeshiftBuffer` zwischen `Backend` und `backendDriver`:
Ring aus 24-ms-Blöcken (Bitrate*3 Bytes) + Zeitstempel (Frame-Zähler, Wanduhr aus FIG 0/10
CIF-Zählung). Modi: `Live` (Durchreichen), `Paused` (Puffer füllt, kein Audio), `Playing
{offset}` (Leser hinkt dem Schreiber hinterher; Leser-Takt = Frame-Rate 41,67 Hz, der
Audio-Sink gibt den Takt vor). Sprung `SeekLive`, `Seek(offset)`, `Skip(±s)`. Event
`TimeshiftState { buffered_s, offset_s, mode, capacity_s }` 2 Hz. Beim Dienstwechsel: Ring
leeren (oder alten Ring als "Snapshot" behalten, falls RAM erlaubt - spätere Idee).

**Interaktionen:**
- **EWS-Alarm**: muss Timeshift verlassen (`SeekLive`) und auf "ASA DE" umschalten; nach
  Ende Rückkehr zum vorherigen Dienst, optional an die alte Position (der Ring des alten
  Dienstes wäre dann weg, außer man behält ihn - siehe Snapshot-Idee). Vorschlag: nach
  Alarm live weiter, mit Hinweis.
- **Timer-Umschaltung**: erzwingt live + Dienstwechsel.
- **Aufnahme**: greift den Live-Strom ab (unabhängig von der Wiedergabeposition); plus neue
  Funktion "Aufnahme ab Pufferposition".
- **Pause bei Fensterschließen/Standby**: Puffer voll -> ältestes verwerfen, UI zeigt
  "Puffer voll, Live-Abstand max".
- **UI**: Slider (links = ältester Punkt, rechts = live), Pause/Play, ±30 s, "Live"-Button,
  Anzeige "-12:34 hinter live"; DLS/Slide der Wiedergabeposition, nicht der Live-Position.

### 5.3 Musikaufnahme und Trennung (MP3-Tags usw.)

**Titelerkennung:**
1. **DL+ (ETSI TS 102 980)**: bereits in `pad-handler.cpp` geparst (`add_toDL2`, Z. 632-709;
   IT = Item Toggle, IR = Item Running, Tags contentType 1 ITEM.TITLE, 2 ITEM.ALBUM,
   3 ITEM.TRACKNUMBER, 4 ITEM.ARTIST, 5 ITEM.COMPOSITION, 6 ITEM.MOVEMENT, 7 ITEM.CONDUCTOR,
   8 ITEM.COMPOSER, 9 ITEM.BAND, 10 ITEM.COMMENT, 11 ITEM.GENRE, 12-30 INFO.*,
   31 STATIONNAME.SHORT, 32 STATIONNAME.LONG, 33 PROGRAMME.NOW, ...). Heute werden nur
   1/8/31/32/33 ausgewertet; V2 wertet alle ITEM.* aus und liefert Event
   `DlPlus { item_toggle, item_running, tags: Vec<(u8, String)> }`. **IR=0 -> kein Musiktitel
   läuft** (Moderation/Nachrichten) - das ist der beste Wort/Musik-Indikator, den DAB bietet.
   Offen: welche Bundesmux-/ARD-Dienste senden DL+ überhaupt? (Am Warntag-Mitschnitt in
   56 Minuten prüfbar - Testaufgabe für M0.)
2. Fallback **DLS-Textwechsel** mit Regex ("Artist - Titel", "Titel / Artist", "Sie hören:").
   Unzuverlässig, nur als Option.
3. **EPG-Sendungsgrenzen** (SPI): schneidet Sendungen, nicht Titel; nützlich für
   "Sendung aufnehmen" (gibt es schon als EpgRecord).

**Schnittgenauigkeit:** DL+ kommt im X-PAD desselben Audio-Frames, ist also technisch
synchron, wird aber vom Sender oft 2-10 s verzögert (manchmal zu früh) geliefert. Deshalb
**nie live schneiden**, sondern aus dem Timeshift-Ring (5.2): bei Titelwechsel zur Zeit t
wird der neue Titel ab `t - vorlauf` (Standard 8 s, konfigurierbar) markiert; das Ende ist
`t_next + nachlauf`. Zur Feinjustage im Grenzbereich: Pegelanalyse des dekodierten PCM
(Suche nach Pegeleinbruch/Pause ±5 s um die Marke; Crossfades bleiben ungenau).
Mindestlänge (Standard 90 s), Maximallänge (15 min), Ausschluss bei IR=0. Ergebnisse als
Vorschlag mit Wellenform in der UI, nicht blind speichern (Frage 3b).

**Format:**

| Format | Bewertung |
|---|---|
| **MP3 via LAME** (MSYS2 `lame 3.100`, LGPL; Rust-Crate `mp3lame-encoder` oder im Kern) | Re-Encoding des dekodierten PCM (HE-AAC 72 kbit/s -> MP3 192-256 kbit/s): Generationsverlust, aber universell abspielbar, ID3v2 überall unterstützt. **Empfehlung als Standard**, weil der User ausdrücklich "MP3 Tags" nennt |
| **AAC-Passthrough** (.m4a) | Verlustfrei: die AUs aus `mp4Processor` (LATM-Rahmen entfernen) in einen MP4-Container mit `AudioSpecificConfig`. **Fallstrick:** DAB+ nutzt AAC mit **960-Sample-Frames** (`frameLengthFlag=1`), nicht 1024. ADTS kann das nicht signalisieren; MP4/esds kann es, aber viele Player/Decoder (Windows Media Foundation, ältere Geräte) unterstützen 960-Frame-AAC nicht; FFmpeg/VLC ja. Als **Archiv-Option** anbieten ("Original-AAC zusätzlich sichern"), nicht als Standard |
| FLAC/WAV des PCM | verlustlos gegenüber PCM, aber Quelle ist lossy; 5-10x größer als MP3; nur für "Roh" sinnvoll. WAV existiert heute schon (Audio-Dump) |

**Tags (ID3v2.4, Rust `id3`; für .m4a `mp4ameta`):** TIT2 Titel, TPE1 Artist, TALB
(ITEM.ALBUM, sonst Sendername), TDRC Datum/Zeit, TCON Genre (ITEM.GENRE oder PTy aus
FIG 0/17 -> `dab-tables`), TRCK, TPE2 Band, TCOM Composer, COMM "Sender / Ensemble /
Kanal / Frequenz", TPUB Sender, **APIC** (MOT-Slide zum Titelzeitpunkt, sonst
SPI-Logo), TXXX DAB-SId. Dateiname `data/music/<Sender>/<yyyyMMdd_HHmm> <Artist> - <Titel>.mp3`.

**Ort:** Erkennung (DL+-Events, PCM-Pegel) im **Kern**; Schnittentscheidung, Encoding,
Tagging in der **Rust-App-Schicht** (`dab-music` Crate: liest AAC-Blöcke aus dem
Timeshift-Ring per `Command::ExportRange{from,to}`, dekodiert über den Kern oder
re-dekodiert selbst, encodiert MP3). Alternativ Encoding im Kern (LAME ist in MSYS2 da);
Rust-Seite ist flexibler (Crates `mp3lame-encoder`, `id3` sind reine MSVC-Builds).

**Lizenz (sachlich):** LAME ist LGPL, mit GPLv3 kompatibel. FDK-AAC steht unter der
Fraunhofer-FDK-Lizenz, die nach verbreiteter Auffassung (Debian: non-free; FSF) nicht
GPL-kompatibel ist; die heutige `Qt-DAB.exe` (GPLv3) mit `libfdk-aac-2.dll` steht in dieser
Grauzone, ebenso `libdabcore` in V2. Praktikable Wege: (1) faad2 (GPLv2+) als Standard und
FDK als **optionale, zur Laufzeit geladene** Bibliothek (wie libhackrf heute), die der
Nutzer selbst ablegt; (2) Dokumentation in THIRD_PARTY_NOTICES wie heute belassen. Da der
Fork Upstream-Code unter "GPLv2 or later" enthält, kann keine Linking-Ausnahme ergänzt
werden. Empfehlung: Weg (1) für V2 vorsehen, Entscheidung beim User (Frage 20).

### 7.2 Thread-Modell im Kern

```
libhackrf-USB-Thread ──putData──> RingBuffer<complex<int8>> (4 M, 2 s)
        │                                   │ getSamples (Blocking-CondVar statt usleep-Poll)
        │                              OFDM-Thread (std::thread): Sync, FFT, Demap,
        │                                   FIC inline (fib-decoder), TII
        │                                   └── 55 296 Soft-Bits/CIF ──> mscHandler
        │                                        └── Backend-Thread je aktivem Dienst (heute
        │                                            QThread/QSemaphore; V2: 1 Thread, CondVar):
        │                                            Deinterleave, Viterbi, RS/Firecode,
        │                                            ──> TimeshiftBuffer (Hardbits, 24 ms) ──>
        │                                            mp4Processor -> FDK -> PCM-Ring
        │                                            PAD/MOT (Events)
        └── (IQ-Dump-Writer optional)          Audio-Thread: PCM-Ring -> 48k-Konverter ->
                                               Lautstärke -> Pegel -> PortAudio-Ring;
                                               WAV/MP3-Writer optional
Kommando-Thread (stdin-Reader in dabcored): parst, legt Kommandos in eine Mutex-Queue;
   OFDM-Thread wendet Quelle/Kanal-Kommandos zwischen zwei Frames an, Backend-Thread die
   Dienst-Kommandos, Audio-Thread Lautstärke/Timeshift.
Event-Thread (stdout-Writer): alle Kernthreads schreiben in eine MPSC-Queue (bounded 4 096,
   für latest-wins-Events ein Slot je Typ); der Writer serialisiert und schreibt.
```

Backpressure: Device-Ring überläuft still (heute so; V2 zählt `AudioUnderrun`/`Overrun`
und meldet sie). Der Event-Writer darf nie blockierend auf einen langsamen Leser warten:
bei voller Queue werden latest-wins-Events ersetzt, lückenlose Events blockieren den
Erzeuger kurz (Backend-Thread), was bei einer Pipe nie passiert. Audio-Ring bleibt im Kern
(PortAudio); Besitzer ist der Audio-Thread.

### 7.3 crossbeam vs. tokio

Kern-Threads sind synchron (DSP, blockierende USB/PortAudio-Callbacks); die Rust-Seite
(`dab-core::IpcBackend`) hat zwei blockierende Threads (stdout-Reader, stdin-Writer) und
gibt `crossbeam::channel::{Sender<Command>, Receiver<Event>}` heraus. Tauri selbst läuft
mit tokio; die Brücke ist ein `std::thread`, der `Receiver<Event>` liest und `app.emit`
ruft (thread-safe). **tokio-mpsc ist nicht nötig**; falls später ein WebSocket-Remote
kommt, wird der crossbeam-Receiver dort per `spawn_blocking` angebunden. Empfehlung:
crossbeam (bounded) für alles außerhalb von Tauri.

| **M0** | Workspace + Headless-Kern am Replay | `v2/` anlegen; `libdabcore` aus v1-Quellen Qt-frei portieren (Abschnitt 2.3); `dabcored --file Warntag.uff --events out.jsonl --wav out.wav`; `dab-api`, `dab-core`, `dab-cli` | 3 Wochen | Event-Log zeigt Sync, "DR Deutschland (10BC)", Dienste, DLS, EWS-Phasen mit denselben Zeitpunkten wie v1; WAV bit-identisch zum v1-Audio-Dump |

Gesamt: 12-15 Wochen konzentriert; nebenher entsprechend länger. Die Reihenfolge M0 -> M1 vor
jeder GUI-Zeile ist bewusst: sie beantwortet die Toolchain-/Architekturfrage mit einem
laufenden Artefakt, und das Warntag-Replay wird zum Regressionstest.

### 8.2 Spikes (Prototypen, je 1-2 Tage, vor M0)

1. **IPC-Spike**: `dabcored`-Stub (C++, MinGW), der 20 Hz Fake-Events + 384 kB/s Fake-PCM
   über stdout schickt; Rust-`dab-core` liest, misst Latenz/CPU; Tauri-Fenster zeigt
   Zähler. Klärt Prozess-Kopplung, `CREATE_NO_WINDOW`, Beenden, Serialisierung.
2. **Kern-Spike**: Nur `ofdm-handler` + `fib-decoder` + `sample-reader` + `xml-file-source`
   ohne Qt kompilieren (Stubs für Events) und am 60-s-Referenzfile "Ensemble gefunden"
   loggen. Klärt, wie zäh die QString-Entflechtung in `fib-decoder.cpp` wirklich ist.
3. **DL+-Spike**: `dabcored` am Warntag-Mitschnitt für 3-4 Dienste laufen lassen und alle
   DL+-Tags loggen -> beantwortet, ob die Musik-Trennung auf DL+ bauen kann.
4. **AAC-960-Spike** (nur falls Passthrough gewünscht): Frame-Dump `.aac` aus v1 in MP4
   muxen (ffmpeg -c copy) und in Windows Media Player/VLC/Handy testen.

### 8.3 Risiken

| Risiko | Wahrscheinlichkeit | Wirkung | Gegenmaßnahme |
|---|---|---|---|
| Entflechtung `fib-decoder`/`pad-handler` bricht Empfang subtil (Charset, EWS-Locations) | mittel | hoch | Bit-Vergleich mit v1 am Replay; v1 bleibt Referenz |
| Timing-Regression ohne Qt-Thread-Semantik (usleep-Polls, Semaphore-Timeouts) | mittel | mittel | CondVar-basierte Übergaben, CPU-Messung im M0 |
| WebView2/Frameless-Details (Drag, DPI, Transparenz) | niedrig | niedrig | Tauri-Doku, Spike |
| Tauri-Event-Durchsatz bei Debug-Scopes | niedrig | niedrig | nur bei geöffnetem Panel, binär |
| FDK-AAC-Lizenz beim öffentlichen Release | bekannt | mittel | faad2-Standard, FDK optional (Frage 20) |
| Timeshift-RAM bei "frei definierbar" (z. B. 24 h = 1 GB) | niedrig | mittel | Obergrenze RAM 2 h, darüber Disk-Ring |
| Zwei Toolchains im Alltag (MSYS2-Shell für Kern, PowerShell für Cargo) | sicher | niedrig | `tools/build-core.ps1` kapselt MSYS2 |
| Scope-Creep durch "alle Funktionen" (Journaline, Karte, 12 SDRs, Scopes) | hoch | hoch | Feature-Liste 5.4 vor M3 mit dem User streichen (Frage 19) |

## 9. Fragen, Anregungen und zusätzliche Ideen an den User

Jede Frage ist einzeln stellbar; Reihenfolge = Priorität.

**1. Rust-Rewrite oder C++-Kern kapseln?** Kontext: Der Wunsch "cargo workspace, dab-core,
crossbeam" liest sich wie Rust im Kern; der DSP ist C++ und in 13 Stufen optimiert, ein
Rust-Rewrite ist schon einmal gescheitert. Empfehlung: C++-Kern Qt-frei als `libdabcore`
behalten, `dab-core` ist das Rust-Crate, das ihn kapselt und die Kanäle liefert; ein
Rust-Kern bleibt später hinter derselben API möglich.

**2. Kern als eigener Prozess (IPC) oder in-process (C-ABI-DLL)?** Kontext: MinGW-Kern vs.
MSVC-Rust/Tauri. Empfehlung: eigener Prozess `dabcored.exe` über stdin/stdout; keine
ABI-Grenze, Crash-Isolation, und der Prozess ist zugleich das Headless-Testwerkzeug.

**3. Audio-Ausgabe im Kern (PortAudio, wie heute) oder in Rust (cpal)?** Empfehlung: im Kern
(M1 schneller, bewährt); cpal als spätere Alternative.

**4. Timeshift: was puffern, wie lang, wo?** Kontext: pro Dienst (~40 MB/h RAM, Puffer
beginnt bei Dienstwechsel neu) vs. ganzes Ensemble (8 GB/h auf Disk, Rückspulen über
Dienste hinweg). Empfehlung: pro Dienst im RAM, Standard 60 min, Obergrenze 2-3 h,
optional Disk-Ring; Wunsch nach Ensemble-Timeshift bitte explizit äußern.

**5. Timeshift und EWS-Alarm:** Alarm springt auf live und schaltet um; nach Alarmende
zurück auf den alten Dienst live (Puffer verloren) oder Puffer des alten Dienstes
"einfrieren" und an alter Stelle weiterhören? Empfehlung: live weiter mit Hinweis
(einfacher, klar).

**6. Musikaufnahme: MP3 (LAME, Re-Encoding) als Standard, AAC-Passthrough als Archivoption?**
Kontext: DAB+-AAC hat 960-Sample-Frames, die viele Windows-Player nicht abspielen.
Empfehlung: MP3 192-256 kbit/s + ID3v2.4 mit Cover; Passthrough optional.

**7. Musik-Trennung: automatisch speichern oder Vorschlagsliste mit Freigabe?** Kontext:
DL+ kommt zeitversetzt; Schnittmarken sind ±5 s ungenau. Empfehlung: Vorschlagsliste mit
Wellenform, Vor-/Nachlauf einstellbar, "alle übernehmen"-Knopf.

**8. Presets: 10 feste Slots mit Tasten 1-9/0, Belegen per Rechtsklick/Langdruck/Strg+Ziffer,
Überschreiben mit Nachfrage?** Empfehlung: ja; bestehende Favoriten-XML einmalig importieren.

**9. GUI-Stil: Classic Compact 1:1 nachbauen oder frei gestalten?** Empfehlung: Layout und
Proportionen übernehmen (Vertrautheit), aber Panels (EPG/Timer/Presets) ein-/ausklappbar
im selben Fenster statt separater Fenster; frameless mit eigener Titelleiste.

**10. Mehrfenster:** nur Alarm-Dialog als eigenes Always-on-top-Fenster, Rest als Panels?
Empfehlung: ja.

**11. Toolchain bestätigen:** MSVC-Rust (installiert) + Tauri; Kern weiter mit MSYS2-GCC/
CMake/Ninja; keine GNU-Rust-Variante. Empfehlung: ja.

**12. Portable-Konzept mit WebView2:** Evergreen-Runtime voraussetzen (Win11 immer, Win10
seit 2022) oder Fixed-Version-Runtime (~180 MB) mitliefern? Empfehlung: Evergreen
voraussetzen, Bootstrapper-Link in der ANLEITUNG; `data/`-Ordner neben der EXE wie heute,
kein Start.bat mehr nötig.

**13. Datei-Wiedergabe (.uff/.iq) bleibt Pflicht?** Kontext: einziger Weg, EWS am
Warntag-Mitschnitt zu testen. Empfehlung: Pflicht in Kern und GUI (Öffnen-Dialog,
Fortschritt, Schleife).

**14. Ist Rust überhaupt gewünscht oder nur die Kanal-Architektur?** Kontext: Tauri erzwingt
Rust in der App-Schicht, aber die App-Logik (Timer, Presets, EPG-Cache) könnte auch in
TypeScript im WebView liegen. Empfehlung: App-Logik in Rust (`dab-app`), damit sie auch
headless/CLI läuft und testbar ist; Svelte nur Darstellung.

**15. Prioritätsreihenfolge der vier neuen Funktionen?** Empfehlung: Presets (klein, sofort
nützlich) -> Timeshift (Kern) -> Musik-Trennung (baut auf Timeshift) -> Rest der Parität
parallel.

**16. Feature-Parität (M3) vor neuen Funktionen (M4)?** Empfehlung: ja, mindestens EWS,
Timer, Aufnahme, EPG, Presets-Import vor Timeshift; sonst zwei halbe Programme.

**17. Idee Headless-CLI und Regressionstests:** `dab-cli replay` mit Event-Snapshot am
Warntag-Mitschnitt (und einem 10-s-Ausschnitt im Repo) als Pflichttest für jeden
Kern-Commit. Einverstanden?

**18. Idee Sleep-Timer und Aufnahme-Nachlauf:** heute gibt es nur den Mute-Timer; V2:
Sleep-Timer (Beenden/Stumm nach n min), Aufnahme mit Vor-/Nachlauf (Timer 2 min früher,
5 min länger). Gewünscht?

**19. Streichliste:** Journaline, TDC/IP-Datagramme, TCP-Server, Uploader, HTTP-Karte,
ETI-Ausgabe, MP2 (DAB alt), 11 fremde SDR-Backends, Legacy-Scheduler/-Zeittabelle,
Classic-GUI-Modus, Qt-Audio - in V2 weglassen? Empfehlung: alles weglassen außer ggf.
ETI/Frame-Dump als Debug-Optionen; Karte später als Leaflet-Panel.

**20. FDK-AAC-Lizenz:** faad2 (GPL) als Standard-Decoder und FDK als optional
nachladbare DLL, oder wie bisher FDK fest? Empfehlung: Umschaltbar per Laufzeit-Laden
(beide Decoder hinter einem Interface, das v1 schon hat), Standard beim öffentlichen
Release faad2, lokal FDK.

**21. Hotkeys:** Ziffern = Presets, Leertaste = Timeshift-Pause/Play, Pfeile = ±30 s / Dienst
prev/next, M = Mute, R = Aufnahme, E = EPG, T = Timer, Esc = Live. Einverstanden?

**22. Versionsname:** intern "V2", nach außen v3.0 (v2.0 ist auf GitHub belegt)? Und Branch
`v3-dev` im selben Repo mit Unterordner `v2/`?

**23. Idee Web-Remote:** das Svelte-Frontend könnte später über einen kleinen
WebSocket-Server (axum) im Browser/Handy laufen (Kern spricht ohnehin Kanäle). Als
Design-Ziel mitführen (kein Fenster-spezifisches JS, alle Daten über Events)?

**24. Idee mehrere Dienste parallel:** Qt-DAB kann Sub-Services/Hintergrunddienste (heute
für EPG-Daten-Dienste genutzt). V2-Kern: mehrere Backends gleichzeitig zulassen (z. B.
Aufnahme von Dienst A bei Hören von Dienst B im selben Ensemble). Gewünscht? Empfehlung:
im API von Anfang an vorsehen (`SelectService` mit `slot: Primary|Background`), UI später.

**25. Idee Debug-Panel:** Spektrum, Konstellation, SNR-Verlauf, TII-Liste, Fehlerzähler als
ausklappbares Canvas-Panel statt eigener Fenster; nur bei Bedarf Daten anfordern.
Einverstanden?

**26. Gain-Persistenz je Frequenz:** heute speichert der HackRF-Handler LNA/VGA/AMP je
Frequenz in der INI (`record_gainSettings`). Beibehalten (Kern liefert/erhält Gain je
Kanal) oder durch die SNR-AGC ersetzen? Empfehlung: beides, AGC als Standard an.

**27. Sprache der GUI:** nur Deutsch, oder de/en umschaltbar wie heute (Systemsprache)?
Empfehlung: de/en mit kleinen JSON-Sprachdateien.
